# RM 自瞄代码审查与改进方向

审查对象是 GitHub 账号 Kisketch 下的 5 个 RM 仓库，对照先前调研的标杆：同济 `sp_vision_25`（整链底座）、深圳大学 2026 神经网络部署库（四关键点检测）、深北莫 `pb2025_rm_vision`（ROS2 生态），以及 2026 赛季规则对弹速的要求。

## 结论先行：内核已经达标，差距在检测、上车链路和弹速实测

你的主仓 `rm-autoaim` 不是一个需要推倒重来的工程。它的整车 EKF、PnP 解算、带阻力弹道和虚拟射击评测，与同济、深北莫采用的事实标准流水线同级，评测体系（基线锁定、回归门禁、消融记录）甚至比多数开源仓库更完整。两条真实视频上整车 EKF 命中率 67.6% / 68.6%、0.32 s 中位预测误差 14.3 / 13.4 px，已经把当前参数空间扫到了平台区——仓库自己的 `docs/BACKLOG.md` 也得出了同一结论：继续调参没有收益。

真正拉开差距的是三处「信息条件」，都不是靠改滤波器参数能补的：

| 优先级 | 改进项 | 为什么排在这里 |
|---|---|---|
| P0 | 实测标定：内参、外参、云台姿态对齐 | 现在内参是假设值（fx = 2400、畸变全 0），相机被当作固定在云台原点，没有 IMU 姿态输入，代码还不能上车 |
| P0 | 检测器换四关键点神经网络 | 现在仍是传统灯条 + MLP 数字分类，是上交 2019 / 深北莫默认包那一代路线；同济 2025 已切换、深大 2026 已给出可直接部署的模型库 |
| P0 | 弹速改为实测/可配输入 | 配置里写死 25 m/s，正好压在 2026 规则 17mm 初速上限上；超速会锁发射机构，弹速不能是常数假设 |
| P1 | 把哨兵分叉收回主线并补齐协议与对齐 | 串口、多目标、前哨站只活在 `rm-sentry-integration` 一个快照分叉里，主仓明确写着「未包含串口协议」，两边正在分叉 |
| P1 | 仓库治理：一处开发、多处归档 | 5 个仓库里有 2 个是同一代码的快照副本，版本已经落后主仓，改错副本的风险是真实的 |

下文逐环节给出证据，再按 P0 / P1 / P2 给出每项的改法和验收标准。

### 已经做对、不要动摇的部分

- 整车模型选对了。点跟踪（point KF）在你的评测里全面落后于整车 EKF（例如视频 3 在 0.32 s 提前量下预测误差 66.6 px 对 14.3 px），这与同济、深北莫收敛到整车 EKF 的结论一致。多板同帧序贯融合、按距离各向异性的观测噪声、yaw 残差的角度包裹，都是细节上正确的实现。
- 评测先行的工作方式是对的。`BASELINE.md` 锁定基线、每项改动用同一组视频和仿真验收、用 hits/s 而不是单一命中率选工作点（避免「提高命中率但打不出伤害」的调参陷阱），这套纪律要保留到后续所有改进里：下面的每项改进都沿用它作验收。
- 已验证否决的方向不要重开。常加速（CA）状态在 25 fps 真实视频上掉 5–7 个百分点、协方差开火门因为 Q 不是标定过的不确定度而几乎拦下所有射击——这两条已经用数据否决，除非信息条件改变（见 P2 的触发条件），不要再投入时间。

### 检测环节的具体证据

传统路线的上限在你自己的两个仓库里都有记录。考核仓 `rm-armor-detection` 的结果报告显示：两条视频有目标帧占比 96.06% / 97.28%，但单条灯条露出（侧对、遮挡）时无法配对成板，最长连续漏检 8 帧；参数是按这批暗光视频标定的，换场景要重调；灯条倾角被限制在竖直 ±40° 内；视频里只有 3 号，其他数字没有样本验证。主仓检测器与它同源，这些限制同样存在。对照深大 2026 的 V8 四关键点模型（其仓库自述在 NUC13 上 6.561 ms、152.43 FPS，Armor mAP50 99.15%），四关键点模型对侧对、倾斜和光照变化的容忍度是结构性的优势，不是参数能追平的。

### 位姿环节的一个隐患：yaw_gain 是经验补丁

`config/default.yaml` 里 `yaw_gain: 1.3` 来自自标定：同一台车两块同时可见的板应相差 90°，实测只有约 69.3° / 69.7°，于是把 yaw 偏差放大 1.3 倍补偿。这个补丁在当前两条视频上有效，但它的根因没有定位——装甲几何、角点定义、假设焦距都可能贡献这个系统性压缩。几何参数目前硬编码在 `include/autoaim/types.hpp`（小板灯条中心距 0.135 m、灯条长 0.055 m；大板 0.225 m / 0.055 m），而先前调研未能从 2026 官方制作规范原件核实装甲的毫米级几何。实测标定（P0 第一项）做完后，应重新检查这个增益是否还需要、需要多少，不要把它当作常数带上车。

## P0：先改信息条件，三项决定能否上车

### P0-1 实测标定与姿态链路：内参、外参、图像-姿态对齐

现状：主仓配置的内参是为测试视频假设的（fx = fy = 2400，畸变全 0），README 明确说焦距无法从这些视频标定；相机被当作位于云台原点、世界系已重力对齐，实车需要的相机到云台外参和拍摄时刻的 IMU 姿态都不存在。仓库已经有棋盘格内参标定工具（`tools/calibrate_camera.py`）和外参 sanity 检查工具，这是好的起点，但还没有实测数据落进配置。

要做的事：

- 用实车相机、镜头、分辨率拍标定图，生成实测内参配置并与假设配置分开保存；`BASELINE.md` 里「换配置旧基线作废」的规则同样适用于实车基线，上车后要建一套实车评测基线，不能再用 25 fps 视频基线判断。
- 实测相机到云台的旋转和平移，填进哨兵仓 `config/sentry.yaml` 已经预留的 `R_cam2gimbal` / `t_cam2gimbal` 字段（该文件注释明确说默认值只对离线视频成立）。
- 补图像与云台姿态的时间对齐：哨兵仓的实车主循环 `apps/sentry_robot.cpp` 现在是先读一帧、再以处理时刻的时间戳去查串口姿态，姿态与曝光时刻并不对齐；同济的做法是相机线程产出图像和时间戳、下位机线程按时间戳配对应的云台四元数。上车帧率越高，这个错位折算成的角度误差越大，应在接高速相机之前就把时间戳链路改对：采集时刻打戳、姿态带戳入队、按戳配对。

验收：同一目标在云台静止和匀速转动两种情况下，PnP 解算的世界系位置抖动不劣于静止情形；外参填入后，`yaw_gain` 重新评估并记录结论（保留、减小或删除都要有数据支撑）。

### P0-2 检测器：接入四关键点神经网络，与传统路线并存可切换

现状：见上文检测环节证据。仓库 `docs/BACKLOG.md` 的 B-02 已经立了项（YOLO-pose 四关键点方案），自述阻塞在 GPU 机器和数据集权限两项外部条件上。这个判断是对的，但有一个不需要等 GPU 的先行选项：深大 2026 的部署库已经开源了训练好的 V5/V8 四关键点模型和统一部署接口（OpenVINO / TensorRT 后端可选），可以直接拿它的 V8 模型做接入验证，先回答「四关键点检测在你的两条视频和你的评测体系里到底涨多少」，再决定是否自训。

要做的事：

- 新增一个与现有 `Detector` 同接口的四关键点检测实现，输出契约保持四角点（顺序与现有约定一致）、类别、颜色、大小不变，让 PnP 及之后环节零改动；传统检测器保留为可切换对照，深北莫的 launch 参数切换检测器也是同样做法。
- 计时要分开报：现在单帧约 5 ms 里检测占约 3.7 ms（主仓基线数据），新检测器单独计时对比，不要只看总帧率。
- 重点看侧对召回和角点精度，而不是只看总命中率：BACKLOG B-02 给自己定的验收（侧对召回不低于传统路线的 1.3 倍、关键点中位误差不高于 3 px）可以直接沿用。

验收：两条视频命中率不低于当前回归基准（67.6% / 68.6%，容差按 `BASELINE.md` §10 的 −1.5 个百分点），侧对帧召回达到上述目标，且单帧总耗时劣化不超过 10% 或有明确的帧率预算说明。

### P0-3 弹速：从写死 25 m/s 改为实测输入，并预留分兵种参数集

现状：主仓和哨兵仓的配置都是 `bullet_speed: 25.`，弹道模块只接收这一个常数，并按固定的 `drag_k = 0.019`（注释标明是 17mm 参数）用 RK4 积分。先前调研核实的 2026 规则要点是：17mm 初速上限 25 m/s、超速会锁定发射机构。也就是说，真实弹速只要随温度、气压、摩擦轮状态漂移，写死上限值会同时带来两个问题：弹道解算系统性偏差，以及合规风险。

要做的事：

- 把弹速改成运行时输入：优先用下位机/裁判系统回传的实测初速，没有回传时用可配置的标定值，并明确留出安全余量（不要把标定值就设在上限上）。
- 弹道参数集按弹丸分开：17mm 一套（现 `drag_k` 即是），英雄 42mm 另备一套，解算接口按当前机器人/目标任务选择参数集，而不是全局单例常数。
- 每次开火决策使用的弹速要能被记录进评测输出，方便复盘「打偏是否来自弹速漂移」——你现有的逐发诊断（`docs/miss_analysis.md` 的做法）正好能承接这项数据。

验收：用仿真注入弹速偏差（例如真实弹速比设定低 1–2 m/s）对比改前改后：改后命中率对弹速偏差的敏感度应显著下降，且评测报告中能逐发看到所用弹速。

## P1：把哨兵分叉收回主线，补齐协议、火控前馈与工程治理

### P1-1 回合并哨兵仓的增量，而不是长期维护两个核心

哨兵仓里有三块主仓没有的真实能力：前哨站跟踪（三块板、单一半径、独立高度过程噪声，`outpost_armor_pitch_deg: -15` 与步兵板反向）、按标签的多目标管理（距离缩放的关联门、丢失轨复用、优先级选靶 `["3", "4", "1", "2", "guard", "base", "outpost"]`）、以及串口收发。建议把这三块以模块形式并入主仓（多目标管理放在单目标 `RobotTracker` 之上，而不是改跟踪器本身），哨兵仓随后冻结为快照。合并时以主仓最新跟踪器为准：哨兵仓跟踪器文件与主仓差异最大，是合并时最需要逐项对账的部分，不要整文件覆盖。

多目标关联目前是贪心最近邻加标签匹配，在两台车靠近时有串靶风险（哨兵仓代码注释里已经记录了关联门按距离缩放、丢失轨门限从 2 倍收紧到 1.4 倍的原因）。合并后若多目标成为常用模式，再评估是否升级为全局指派；现在先保留贪心实现和它的调参记录。

### P1-2 串口协议补校验与失效保护

哨兵仓的旧协议解析只校验帧头 `AA BB`（姿态帧连帧尾都不校验），控制帧除帧头帧尾外没有校验和；串口在 115200 波特率下误码会直接变成错误姿态或错误开火指令。建议：与电控协商在协议里加 CRC 或至少校验和，解析失败计数要可见；姿态数据超时（例如超过若干帧没有新姿态）时应停止开火而不是继续用旧姿态外推。现有的「目标丢失后 0.5 s 内保持下发但不开火」（HoldFound）是合理的失效保护，保留。

另外，哨兵仓把 yaw 角速度塞进旧协议的 `ui_x` 字段下发（代码注释说明是沿用旧下位机映射），这是协议债：合并时应与电控确认前馈量的正式字段，避免以后有人按字段名误用。

### P1-3 火控：把速度前馈从「评测参数」变成正式能力

你的瞄准器已经有延迟 + 飞行时间的迭代求解和选板滞回，缺的是同济轨迹规划器那一层：对云台运动本身做规划并下发前馈。仓库 BACKLOG B-01 已经量化了收益——仿真中云台速度前馈从 0 到 1.0，硬平移场景命中率 43.8% → 51.1%，整体均值 78.0% → 79.2%，且明确需要电控配合接收 yaw rate。哨兵仓实车循环里已经在用相邻帧指令差分算 yaw 角速度并下发，说明接口意向存在；建议把这件事正式推进：视觉侧固定输出 `yaw, yaw_rate, pitch, pitch_rate`，与电控联调验收以 B-01 自定的标准为准（硬平移类场景实车收益不低于 5 个百分点且不伤稳态精度）。中心模式（转速高于 12 rad/s 才启用）在 25 fps 下已被你的数据证明不优于装甲模式，帧率上到 100 fps 以上后值得重测一次，阈值不要照搬现在的值。

### P1-4 仓库治理与回归自动化

- 开发只在 `rm-autoaim` 进行；`rm-autoaim-clean` 和 `rm-complete` 明确标注为只读快照（README 顶部注明快照日期与对应提交，后续不再同步修改），`rm-armor-detection` 冻结为考核交付。
- 主仓的回归门禁 `tools/regression.py` 目前依赖不在仓库内的两条视频，README 也提到 CI 跑不了它。建议补一条轻量路径：把检测缓存或一小段脱敏测试视频纳入 CI 可用的测试资产，让每次提交至少能自动跑过单元测试 + 小规模回归，而不是只靠本机手动跑。考核仓已有的 GitHub Actions（构建零警告 + 合成视频冒烟）可以作模板参考。
- 文档继续集中在主仓：哨兵仓的部署与集成文档在合并后迁入主仓，避免同一问题两处记录、结论不一致。

## P2：有触发条件再做，现在做是浪费

| 事项 | 为什么现在不做 | 触发条件 |
|---|---|---|
| 硬平移运动模型（CA / IMM） | CA 已在 25 fps 数据上验证失败，根因是加速度不可观测；仿真硬平移场景 43.2% / 无旋转硬平移 14.6% 是信息不足，不是模型阶数不足 | 相机升到 100 fps 以上，或引入自身运动补偿（IMU/里程计）后重测 |
| 双板 90° 公共偏置状态 | 整车 EKF 观测模型已经隐含板间 90° 关系，BACKLOG B-04 已评估为信息重复；真正的缺口是相关误差建模，成本 1–2 天且收益不确定 | 双板同帧占比上升，或 P0-1 标定后 yaw 偏差仍被证明是主要误差项 |
| 能量机关（打符）链 | 主仓明确未包含；它是独立的第二任务链（五关键点、相位预测、径向精度），与装甲自瞄只共用弹道和火控外壳 | 队伍任务明确分配打符后，参考深大 `RP-26Rune` 的完整实现另起模块 |
| 自训四关键点模型与数据集扩充 | 现在只有两条视频、一个 3 号红色目标，数字分类器也只验证过「3」；先用深大开源模型验证路线，再谈自训 | P0-2 接入验证显示开源模型不够用，或比赛需要覆盖更多颜色/编号/距离段时，先补数据采集与标注流程 |
| 哨兵导航对接 | 导航框架（先前调研的北理珠 `YH_Sentry_nav_2026`）解决的是哨兵移动与决策，与自瞄的接口在目标/朝向指令层，不在视觉流水线内 | 哨兵整车联调阶段，由导航/决策侧定义接口后再对接 |

## 建议执行顺序与验收

1. **P0-3 弹速输入化**（改动最小、先行）：弹速改为运行时输入 + 分弹丸参数集，仿真注入偏差验收。
2. **P0-1 标定与对齐**：实测内参落配置，外参填入哨兵配置，时间戳-姿态对齐改造；完成后重评 `yaw_gain`，并新建实车基线。
3. **P0-2 四关键点检测接入**：先用深大开源 V8 模型验证，传统检测器保留可切换；用现有回归门禁验收，不达标不替换默认。
4. **P1-1 / P1-2 哨兵回合并与协议加固**：多目标、前哨站、串口并入主仓，协议加校验与姿态超时停火。
5. **P1-3 / P1-4 前馈联调与仓库治理**：与电控联调速度前馈；快照仓标注只读，CI 补轻量回归。

每一步的通用验收线沿用主仓 `BASELINE.md` §10：两条视频命中率劣化不超过 1.5 个百分点、0.32 s 预测误差增加不超过 1.5 px、单帧耗时劣化不超过 10%、单元测试必须全过。上车相关步骤另建实车基线，不与视频基线混用。

## 审查边界

- 本次是静态代码与文档审查：逐仓阅读了 README、基线报告、配置、核心源码（检测、位姿、跟踪、瞄准、弹道）与哨兵仓的串口、多目标、前哨站实现；没有在本机编译运行，也没有实车数据，因此所有性能数字均引自各仓库自带的报告与基线文件，未做独立复测。
- 哨兵仓与主仓的差异是按文件与模块级对账，没有做逐行 diff 全量比对；回合并时仍需逐项核对跟踪器差异。
- 装甲板毫米级几何（`types.hpp` 中的硬编码值）与 2026 规则参数，本次沿用先前调研的结论：未能从官方规范原件核实，做 PnP 模型点和弹道参数前必须以官方手册原件复核。
- 先前调研中未能核实的 Gitee 旋转框关键点检测仓库，本次同样不作引用；四关键点路线的依据是深大与同济已核实的开源实现。
